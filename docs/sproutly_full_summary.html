Product definition
Core purpose
A beginner hobbyist garden companion app for people growing plants on balconies or indoors. Builds confidence and makes gardening feel fun — not a power tool, more like Duolingo for plants.
Primary user
Sam, 28 — first-time plant parent. Has a sunny balcony. Excited but nervous about killing plants. Doesn't know botanical terminology and doesn't want to read a manual.
Platform
Web-first, hybrid. Desktop and tablet browser as primary. Mobile web fully responsive from day one. Native iOS/Android apps out of scope for v1.
North star feeling
"This is fun and I want to learn more." Every feature must reduce fear, build curiosity, or celebrate a small win.

Onboarding flow — decided
8 steps (< 3 min target)
Step 1 — Sign up (email or Google/Apple OAuth)
Step 2 — Welcome: name + location (for climate advice)
Step 3 — Choose space: balcony, indoors, garden bed, not sure
Step 4 — Experience level (beginner pre-selected)
Step 5 — Starter pack selection (3 curated bundles)
Step 6 — Meet your first plant (care card + nickname)
Step 7 — Enable reminders (web push, asked last)
Step 8 — Aha moment dashboard (tasks + tip card)
Key UX decisions
One question per screen — never more
"Skip to dashboard" always visible from step 2+
Notification permission asked last (after emotional investment)
Starter pack pre-selected by space type — user just confirms
No tutorial overlays — dashboard speaks for itself
Flow is resumable — saved to localStorage + server
Plain English only — no botanical jargon on any screen
Beginner mode flag unlocks simplified content app-wide

Technical decisions — decided
Stack
Frontend: React + Zustand (state), localStorage persist
API: Node.js / Express + Passport.js (auth)
Database: PostgreSQL (primary), Redis (sessions, cache, analytics queue)
Auth: JWT + refresh tokens + OAuth 2.0 (Google, Apple)
Push: Web Push API + VAPID keys
CDN: Cloudflare for static assets + API edge caching
Key constraints
Each screen loads in < 1s — no blocking API calls on transition
Onboarding JS bundle < 120 KB gzipped
All API endpoints < 300ms at p95
WCAG 2.1 AA on all onboarding screens
POST /gardens must be a single DB transaction
75 atomic tasks, ~83 dev-days solo / ~6 weeks 2-person team
Open questions — unresolved
OQ-01
What is the monetisation model? Freemium (free up to 5 plants, paid for unlimited + AI diagnosis) is the leading hypothesis but not decided.
Business
OQ-02
Which geocoding provider? Google Maps Platform (accurate, ~$5/1k requests) vs Nominatim/OpenStreetMap (free, slower, weaker for India and non-Western cities).
Engineering
OQ-03
Anonymous / guest onboarding before account creation? Reduces signup friction but adds ~1 day of engineering complexity for session migration.
Product / Engineering
OQ-04
Defer email verification or not? Deferring reduces onboarding friction but risks inflating analytics with junk accounts. Recommendation: defer, add soft nudge on day 3.
Product / Engineering
OQ-05
OAuth flow for web: popup vs redirect? Popup is smoother but blocked by some mobile browsers. Redirect with PKCE + Redis state restoration is more reliable.
Engineering
OQ-06
Push notification scheduling: in-process cron (simple, works to ~10k users) vs BullMQ queue (small overhead, avoids a painful rewrite at scale). Recommendation: BullMQ from day 1.
Engineering
OQ-07
Should the experience level screen (step 4) be skipped entirely, given beginners are always pre-selected? Or does actively choosing it create useful engagement?
Product / UX
OQ-08
Safari fallback for Web Push: Safari < 16.4 does not support the Push API. Affected users get in-app bell only. Is this acceptable at launch, or does it need a different notification strategy?
Engineering
OQ-09
Domain acquisition: sproutly.app should be purchased as the primary action. sproutly.com should be checked — if parked, a direct inquiry to the registrant may be worth pursuing.
Business
OQ-10
Re-engagement strategy for users who complete onboarding but do not return after day 1. Email sequence? In-app? Push nudge? Not yet designed.
